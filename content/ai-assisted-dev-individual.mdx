## 1. "AI가 해줬어요" 증후군

{/*
  - "이거 고쳐줘" → "이건 되니 저게 안돼, 고쳐줘" → 코드가 개판이 되는 패턴 묘사
  - Jake Nations (Netflix Staff Engineer)의 "Infinite Software Crisis" 인용
    - 개발자가 이해하는 것보다 빠르게 코드를 생산하는 위험
    - "쉬운 것(easy)"과 "단순한 것(simple)"은 다르다
  - 압도적 생산성으로 모든 코드를 다 뜯어봐야 하면 사람이 병목이 된다
*/}



## 2. Dunning-Kruger로 보는 AI 활용 영역

{/*
  - Dunning-Kruger 효과 간략 설명
  - AI 활용의 두 가지 안전 영역:
    - 확실하게 아는 영역 → AI를 가속기로, 결과 검증 가능
    - 아예 모르는 영역 → AI를 탐색 도구로, 학습 목적
  - 위험 영역: "대충 아는" 구간 → 검증 능력 없이 AI 출력을 신뢰
  - "AI가 해줬어요" 금지가 가장 중요한 이유: 이해 없는 코드는 유지보수 부채
*/}



## 3. Research → Plan → Implement

{/*
  - Jake Nations의 3-phase 프로세스 소개:
    1. Research & Compression — 문제 도메인을 AI와 함께 탐색하되, 핵심을 자기 언어로 압축
    2. Detailed Planning — AI에게 구현을 맡기기 전에 설계를 인간이 확정
    3. Implementation — AI가 코드를 생산, 인간이 검증
  - 각 단계에서 AI가 실패하는 지점을 짚어주면 좋음
*/}

| 단계 | AI의 역할 | 인간의 역할 |
|------|-----------|-------------|
| Research | 자료 탐색, 요약 | 핵심 판단, 압축 |
| Planning | 구조 제안 | 설계 확정 |
| Implementation | 코드 생산 | 검증, 테스트 |

## 4. 할루시네이션을 줄이는 실전 스킬

{/*
  - Voting(다수결): 같은 질문을 여러 세션/모델에 던져서 교차 검증
  - 세션 분리 원칙: Review는 반드시 다른 세션에서 (확증편향 방지)
    - 생성 세션의 컨텍스트가 리뷰를 오염시키는 메커니즘 설명
  - 테스트 코드의 중요성: AI가 만든 코드의 최종 검증자는 테스트
    - 사람이 병목이 되는 상황에서 테스트가 자동화된 검증 레이어 역할
  - Skill 관리: 프로젝트 공유용 vs 개인용 스킬 분리
*/}
