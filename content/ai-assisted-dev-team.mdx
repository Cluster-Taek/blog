## 1. 에이전트 병렬 시대의 새로운 병목

{/*
  - 팀원 모두가 에이전트를 병렬로 돌릴 때 발생하는 현상:
    - 코드 스타일 발산
    - 컨텍스트 비동기화 (A가 변경한 구조를 B의 에이전트가 모름)
    - 컨플릭트 폭발
  - !!중요!! 이슈 단계에서 컨플릭트를 미리 해결해야 하는 이유
    - 코드 레벨의 컨플릭트는 이미 늦은 것
    - 설계 레벨에서 충돌을 합의해야 에이전트가 안전하게 병렬 실행 가능
*/}



## 2. 보일러플레이트와 컨벤션으로 진입점 통제

{/*
  - 초기 구조가 확실한 보일러플레이트 기반 작업이 필수인 이유
  - TypeScript strict + lint 타이트 + 아키텍처 제한
  - Barrel 파일(index.ts)을 통한 진입점 통제
    - AI 에이전트가 참조할 수 있는 명시적 Public API
    - 강제적 컨텍스트 동기화 효과: 에이전트가 index.ts만 봐도 현재 모듈 구조를 파악 가능
  - no-restricted-imports ESLint rule로 깊은 경로 import 차단
*/}

```tsx title="eslint.config.mjs"
// AI 에이전트가 내부 구현에 직접 접근하는 것을 린트 레벨에서 차단
'no-restricted-imports': ['error', {
  patterns: ['@/features/*/internal/*']
}]
```

## 3. Rule-Based 프롬프팅과 지식 계층화

{/*
  - 자유 형식 프롬프트가 팀 환경에서 실패하는 이유
    - 팀원마다 다른 프롬프트 → 다른 결과 → 코드 발산
  - Toss의 "harness" 개념 소개
    - Plugin/Marketplace로 팀 노하우를 패키징
    - 가장 LLM을 잘 다루는 엔지니어의 워크플로우를 팀 전체에 배포
  - Global / Domain / Local 계층화 지식 관리
  - RAG 대비 Plugin의 예측 가능성이 높은 이유
*/}

| 계층 | 내용 | 예시 |
|------|------|------|
| Global | 전사 공통 규정 | 보안 정책, 기본 코딩 스타일 |
| Domain | 팀/비즈니스별 지식 | 결제, 정산 등 도메인 특화 로직 |
| Local | 레포지토리 구현 세부사항 | 프로젝트별 규칙 |

## 4. 시스템이 시스템을 검증하는 구조

{/*
  - 비즈니스 로직 단위 테스트 필수 — 커버리지 기준 못 넘기면 머지 불가
  - 코드 리뷰 전용 AI 에이전트 도입 (인간 리뷰와 역할 분리)
  - CONTEXT.md 자동 생성
    - CI/CD 또는 Pre-commit hook으로 자동 업데이트
    - 에이전트가 참조하는 "살아있는 문서" 역할
    - 데일리 스크럼에 해당하는 컨텍스트 동기화 효과
*/}

| 검증 레이어 | 도구 | 시점 |
|-------------|------|------|
| 정적 분석 | ESLint strict + TypeScript strict | 코드 작성 시 |
| 단위 테스트 | Vitest / Jest | Pre-commit / CI |
| 커버리지 게이트 | CI coverage threshold | PR 생성 시 |
| AI 코드 리뷰 | 리뷰 전용 에이전트 | PR 생성 시 |
| 컨텍스트 동기화 | CONTEXT.md 자동 생성 | Pre-commit hook |
